# 团队培训安排

登记成员、创建带容量的培训活动，记录报名、批量取消报名、改报、分场与查看参与名单，并登记、批量更正（含撤销）与查询培训完成记录。

## 运行

需要 Python 3.10 或更新版本，仅使用标准库，无依赖安装步骤。请在本目录运行：

```sh
python3 -m team_planner --root ./state demo
python3 -m unittest discover -s tests -v
```

这是本地命令行程序，不监听网络端口，无账户或密码。`demo` 在指定 root 的临时子目录中读取 examples 样例并演示业务，结束后清理样例状态，不改变现有数据。

## 正常使用

公开 API：`from team_planner import TeamPlanner`，然后 `TeamPlanner(root)`。每个命令接收可选的 JSON 文件，其对象键与 API 方法参数一致。例如：

```sh
python3 -m team_planner --root ./state member examples/members.json
```

JSON 数组会按顺序执行多个独立操作；先前成功操作保留，后续失败不会回滚整批。重跑登记命令遇到已存在的标识会报错。

- `member` → `TeamPlanner.add_member(...)`。参数名见 `core.py` 的公开方法签名。
- `activity` → `TeamPlanner.create_activity(...)`。参数名见 `core.py` 的公开方法签名。
- `enroll` → `TeamPlanner.enroll(...)`。参数名见 `core.py` 的公开方法签名。
- `enroll-batch` → `TeamPlanner.enroll_batch(...)`。输入对象包含 `records`；`records` 必须是非空数组，每项只含 `activity_id` 与 `member_id` 两个字段，两个标识去除首尾空白后须为非空字符串，规范化后同一活动与成员组合不得重复。整组报名一起生效：每项引用的成员与活动均须存在，成员此前不能已报名该活动；同一成员可报名不同日期的多场活动，同一活动可接收多名成员。容量按原名单加上本批全部新增人数判断，已完成报名继续占位；任一新增报名与本人同日另一场活动冲突即拒绝整组，检查同时包含既有报名和本批其他条目，已完成报名仍算冲突，其他成员的报名以及未新增报名日期上的历史冲突不影响本批。未知标识、已报名、最终超员或同日冲突均抛出 `ValueError`。成功按输入顺序向各活动名单末尾追加成员，保留原名单相对顺序，返回与 `enroll` 相同字段的完整活动对象数组，逐项对应输入；同一活动重复出现时，各项都展示最终名单。成功只改变所选报名，完成记录、成员档案、活动其他字段和历史额外字段原样保留，缺少 `completions` 的旧数据继续兼容。任一条件不满足均抛出 `ValueError`，整次失败保持数据文件字节不变，此前没有目录或 `data.json` 时也不创建。顶层 JSON 数组表示多个独立批次，先前成功的批次保留，遇错停止且标准输出为空。
- `preview-enroll` → `TeamPlanner.preview_enrollments(...)`。`enroll-batch` 的只读预览：输入对象同样包含 `records`，结构、逐项规范化与校验规则完全一致（非空数组、每项只含 `activity_id` 与 `member_id`、两个标识去空白后非空、规范化后同一活动与成员组合不重复、成员与活动均存在且成员尚未报名该活动，违反均抛出 `ValueError`，不返回部分预览）。预览只评估本次输入，不提交任何报名，也不依赖当前日期：成功与失败都不改写 `data.json`，也不创建缺失的目录或文件，只把预览对象打印到标准输出。返回对象含 `can_enroll` 与 `records`；`records` 按输入顺序逐项给出规范化后的 `activity_id`、`member_id`，并增加 `remaining_seats` 与 `conflict_activity_ids`。`remaining_seats` 等于活动容量减原名单人数再减本批新增人数，同一活动各项数值一致，超员保留负值，已完成报名仍占席；`conflict_activity_ids` 升序去重列出本人在目标日期报名的其他活动（包含当前报名和本批拟新增报名，排除本条目标活动；已完成报名仍计冲突，其他成员及其他日期的报名不计）。席位不足与冲突同时存在时两类信息全部返回，不因首个阻碍停止；仅当每项剩余席位非负且冲突数组为空时 `can_enroll` 才为 `true`，否则为 `false`，业务阻碍本身不抛异常。数据未变化时，可行预览可按原输入由 `enroll-batch` 提交成功。预览遵循既有整份历史校验，无效历史抛出 `ValueError`，读取文件的操作系统错误保留 `OSError`；缺少 `completions` 的旧数据按无记录处理。顶层 JSON 数组沿用逐项执行语义，遇错标准输出为空。
- `cancel` → `TeamPlanner.cancel_enrollments(...)`。输入对象包含 `member_id`、`activity_ids`；成员标识与每个活动标识去除首尾空白后须为非空字符串，`activity_ids` 必须是非空数组且去空白后无重复。一次调用撤回该成员在全部指定活动中的席位，只有成员存在、每个活动存在、成员在每个活动中均已报名，且在任一活动都没有本人完成记录时才整体生效：其他成员的完成记录不阻止取消，本人在未选中活动的完成记录也不影响操作。各活动只移除该成员，其余参与者相对顺序以及标题、日期、容量均不变，完成记录全部保留；释放的席位可立即继续报名或改报。成功返回更新后的完整活动对象数组（字段与 `activity`、`enroll` 一致），顺序与输入活动顺序一致。任一条件不满足均抛出 `ValueError` 且原有数据文件内容不变；此前没有数据目录或 `data.json` 时取消失败也不会创建。取消不依赖当前日期，过去但尚未登记完成的报名同样可撤回。
- `transfer` → `TeamPlanner.transfer_enrollment(...)`。输入对象包含 `source_activity_id`、`target_activity_id`、`member_id`，三个标识去除首尾空白后须为非空字符串。把该成员的一次报名从原活动转到目标活动：从原活动名单移除（其余成员相对顺序不变）并追加到目标活动名单末尾，原活动释放一个名额、目标活动占用一个名额，成功返回目标活动完整对象（字段与 `activity`、`enroll` 一致）。任一活动或成员不存在、两项活动相同、成员未报名原活动或已报名目标活动、目标活动已满都会被拒绝。成员在原活动已有本人完成记录时拒绝改报（其他成员的完成记录不阻止操作，任何完成记录都不会被删除或迁移）；成员在目标日期已报名第三个活动时拒绝，检查排除原活动与目标活动，已完成培训的报名同样算冲突。成员档案及两项活动的标题、日期、容量均不变。
- `transfer-batch` → `TeamPlanner.transfer_enrollments(...)`。输入对象包含 `changes`；`changes` 必须是非空数组，每项只含 `source_activity_id`、`target_activity_id`、`member_id` 三个字段，三个标识去除首尾空白后须为非空字符串，同一成员在组内只能出现一次。整组改报一起生效：成员与两场活动均须存在、两场不同、成员原先已报名原活动且未报名目标；成员在原活动有本人完成记录时拒绝整组，其他成员的完成记录不阻止操作。容量与同日冲突按整组完成后的报名判断：目标原先满员但最终未超员时允许转入，满员活动间的席位互换或循环调整可一次生效；任一转入成员在目标日期仍报名另一活动则拒绝整组，已完成报名同样算冲突，无关的历史冲突不阻止本组。最终名单保留未移出成员的相对顺序，移入成员按输入顺序追加到目标名单末尾。成功返回目标活动完整对象数组（字段与 `transfer` 结果一致），逐项对应输入顺序，同一目标出现多次时各项均反映整组完成后的最终名单。成功只改变本组所涉报名，成员档案、活动其他字段、额外字段及全部完成记录保留（完成记录不迁移），缺少 `completions` 的旧数据继续兼容。任一条件不满足均抛出 `ValueError`，整次失败保持数据文件字节不变，此前没有目录或 `data.json` 时也不创建。顶层 JSON 数组表示多个独立批次，先前成功的批次保留，遇错停止且标准输出为空。
- `preview-transfer` → `TeamPlanner.preview_transfer_enrollments(...)`。`transfer-batch` 的只读预览：输入对象同样包含 `changes`，结构、逐项规范化与校验规则完全一致（非空数组、每项只含 `source_activity_id`、`target_activity_id`、`member_id`、三个标识去空白后非空、规范化后成员不重复、成员与两场活动均存在、两场不同、成员已报名原活动且未报名目标，违反均抛出 `ValueError`）。预览不提交任何改报：成功与失败都不改写 `data.json`，也不创建缺失的目录或文件，只把预览对象打印到标准输出。返回对象含 `can_transfer` 与 `changes`；`changes` 按输入顺序逐项给出规范化后的 `source_activity_id`、`target_activity_id`、`member_id`，并增加 `has_completion`、`remaining_seats`、`conflict_activity_ids`。`has_completion` 为布尔值，仅表示本人在原场是否有完成记录（其他成员的记录、缺少 `completions` 的旧数据均视为无）；`remaining_seats` 是目标容量减整组拟议改报后的人数，超员保留负值，同一目标在各项中的数值一致，有完成记录的请求也参与人数计算；`conflict_activity_ids` 升序去重列出本人在目标日期仍报名的其他活动（比较采用整组改报后的报名，排除原场与目标场，已完成报名仍计冲突，其他成员报名不计，无关的历史冲突不阻止方案）。三类阻碍同时存在时全部返回；只有每项均无完成记录、无冲突且剩余席位非负时 `can_transfer` 才为 `true`，否则为 `false`。2026-10-15 两场满员培训互换席位、且无完成记录与第三场冲突时预览可行。输入合法但存在业务阻碍时返回 `can_transfer` 为 `false` 而非报错。预览遵循既有整份历史校验，无效历史抛出 `ValueError`，读取文件的操作系统错误保留 `OSError`；缺少 `completions` 的旧数据按无完成记录处理。顶层 JSON 数组沿用逐项执行语义。
- `split-activity` → `TeamPlanner.split_activity(...)`。培训分场：输入对象包含 `source_activity_id`、`activity_id`、`title`、`on`、`capacity`、`member_ids`，一次把所选未完成人员移到新活动，新场创建和报名转移一起生效。活动标识、标题和成员标识去除首尾空白后须为非空字符串；`member_ids` 必须是非空数组且规范化后无重复；`on` 只接受无首尾空白、真实存在的 `YYYY-MM-DD` 字符串；`capacity` 须为非布尔的正整数且不少于转移人数。原场与成员均须存在，新场标识不得已存在；所选成员均须已报名原场且没有本人的原场完成记录（他人的完成记录不阻止分场，任何完成记录都不会被删除或迁移）；任一所选成员在新日期仍报名第三场活动时拒绝分场，已完成报名也算冲突，原场被排除，无关人员或其他日期的历史冲突不影响操作。成功返回含 `source_activity` 与 `new_activity` 的对象，两项都是既有活动对象的完整结构：新场名单按成员输入顺序排列，原场保留未移出人员的相对顺序，空名单的原场仍保留。分场保留原场其他字段、成员档案、全部完成记录及历史额外字段，新场仅含标准活动字段且无完成记录；新场与原场同日也可成功，规则不依赖当前日期。缺少 `completions` 的旧数据继续兼容，整份历史无效抛出 `ValueError`，文件读写错误保留 `OSError`。任一条件不满足均抛出 `ValueError`，整次失败不创建新场、不转移报名，已有 `data.json` 字节不变，缺失目录或文件不创建。查询和导出随即反映新名单。顶层 JSON 数组表示多个独立分场，先前成功的分场保留，遇错停止且标准输出为空。
- `reschedule` → `TeamPlanner.reschedule_activity(...)`。输入对象包含 `activity_id`、`on`；新日期须为真实存在的 `YYYY-MM-DD` 字符串。成功返回完整活动对象（仅 `on` 改变，标题、容量、参与者及顺序不变）。新日期与原日期相同时直接返回原活动，不重写数据。活动已有任何完成记录，或某位当前参与者已报名新日期当天的另一活动时拒绝调整。
- `reschedule-batch` → `TeamPlanner.reschedule_activities(...)`。输入对象包含 `changes`；`changes` 必须是非空数组，每项只含 `activity_id` 与 `on` 两个字段，标识去除首尾空白后须为非空字符串、规范化后不得重复，活动须存在，日期只接受无首尾空白、真实存在的 `YYYY-MM-DD` 字符串。整组调整一起生效：冲突按全部活动调整后的最终日期判断，可行的互换不会因中间状态被拒绝。仅日期实际改变的活动受约束——其任一参与者在最终日期已报名另一场活动（无论是否在本组内、是否已完成）即拒绝整组，只有其他成员报名不算冲突；实际改期的活动存在任何完成记录时拒绝。日期不变的条目允许保留完成记录或原有冲突，全组日期都不变时返回原活动且不重写文件，无关的历史冲突不阻止操作。成功返回完整活动对象数组（字段与 `reschedule` 结果一致），顺序与输入一致，仅各所选活动的 `on` 改变，成员档案、标题、容量、参与者顺序与完成记录均保留。任一条件不满足均抛出 `ValueError`，整次失败保持数据文件字节不变，此前没有目录或 `data.json` 时也不创建。顶层 JSON 数组表示多个独立批次，先前成功的批次保留，遇错停止且标准输出为空。
- `preview-reschedule` → `TeamPlanner.preview_reschedule_activities(...)`。`reschedule-batch` 的只读预览：输入对象同样包含 `changes`，结构、逐项规范化与校验规则完全一致（非空数组、每项只含 `activity_id` 与 `on`、标识去空白后非空且不重复、活动存在、日期为无首尾空白的真实 `YYYY-MM-DD`，违反均抛出 `ValueError`）。预览不提交任何改期：成功与失败都不改写 `data.json`，也不创建缺失的目录或文件，只把预览对象打印到标准输出。返回对象含 `can_reschedule` 与 `activities`；`activities` 按输入顺序逐项给出 `activity_id`、`previous_on`（原日期）、`on`（申请日期）、`completion_member_ids` 与 `conflicts`。仅日期实际改变的活动检查阻碍，日期不变的条目两个数组都为空；`completion_member_ids` 升序列出该活动有完成记录的成员，`conflicts` 只收录当前参与者中有同日冲突者，按 `member_id` 升序返回对象，每项含 `member_id` 与升序去重的 `activity_ids`（本人报名的其他最终同日活动，排除本场；比较日期时采用整组申请后的日期，组外活动沿用原日期，已完成报名仍计冲突，其他成员的报名不计）。完成记录与冲突同时存在时两类信息全部返回；所有阻碍数组都为空时 `can_reschedule` 才为 `true`，可行的日期互换可以通过，无关历史冲突不阻止方案。输入合法但存在业务阻碍时返回 `can_reschedule` 为 `false` 而非报错。预览遵循既有整份历史校验，无效历史抛出 `ValueError`，读取文件的操作系统错误保留 `OSError`；缺少 `completions` 的旧数据按无完成记录处理。顶层 JSON 数组沿用逐项执行语义。
- `roster` → `TeamPlanner.roster(...)`。参数名见 `core.py` 的公开方法签名。
- `list` → `TeamPlanner.activities(...)`。参数名见 `core.py` 的公开方法签名。
- `complete` → `TeamPlanner.record_completion(...)`。输入对象包含 `activity_id`、`member_id`、`completed_on`；完成日期须为真实存在的 `YYYY-MM-DD` 日期，且不早于活动日期。成功返回单条完成记录（含活动的 `title`、`on`）。
- `complete-batch` → `TeamPlanner.record_completions(...)`。输入对象包含非空 `records` 数组，每项只含 `activity_id`、`member_id`、`completed_on` 三个字段，允许跨活动、跨成员提交。活动与成员标识去除首尾空白后须为非空字符串，去空白后相同的活动与成员组合视为重复：整组拒绝，即使完成日期相同也不合并。日期只接受无首尾空白、真实存在的 `YYYY-MM-DD` 字符串，不早于对应活动日期，不受当前日期限制。每条记录的活动与成员均须存在、成员已报名该活动、且没有该活动的本人完成记录（其他成员的完成记录不阻止登记，组内前一条也不得与后一条形成重复组合）。任一类型或业务条件不满足均抛出 `ValueError`，整组不新增任何记录，已有 `data.json` 字节不变，缺失的数据目录或文件不创建。成功只增加所选完成记录，返回记录数组，字段与 `complete` 的结果相同，顺序与输入一致；既有完成记录、成员档案、活动字段、参与者顺序和额外字段全部保留，报名继续占用容量。顶层 JSON 数组表示多个独立批次，此前成功批次保留，遇错停止且标准输出为空。
- `correct-completions` → `TeamPlanner.correct_completions(...)`。输入对象包含非空 `records` 数组，每项只含 `activity_id`、`member_id`、`completed_on` 三个字段，允许跨活动、跨成员更正。活动与成员标识去除首尾空白后须为非空字符串，去空白后相同的活动与成员组合视为重复：整组拒绝，即使完成日期相同也不合并。`completed_on` 为 `null` 表示撤销该完成记录；否则只接受无首尾空白、真实存在的 `YYYY-MM-DD` 字符串，不早于对应活动日期，不受当前日期限制。每条记录的活动与成员均须存在、成员已报名该活动、且已有本人的完成记录（其他成员的完成记录不影响更正，没有本人记录时无论改成日期还是撤销都拒绝）。整组一起生效：任一类型或业务条件不满足均抛出 `ValueError`，整组不改任何记录，已有 `data.json` 字节不变，缺失的数据目录或文件不创建。成功只改变所选完成记录：新日期替换原日期，`null` 仅删除本人该条记录；撤销不取消报名、不释放席位。返回结果数组，顺序与输入一致，每项含 `activity_id`、`member_id`、`title`、`on`、`previous_completed_on`（原日期）与 `completed_on`（新日期，撤销为 `null`）。新日期与原日期相同的条目成功返回但不产生变化，全组均无变化时不重写文件。名单顺序、成员档案、活动字段、其他完成记录和额外字段全部保留；`completions`、`schedule` 与 `export-schedule` 随即反映新日期或未完成状态，撤销后的报名重新适用取消、改报与改期的原规则。缺少 `completions` 的旧文件视为没有可更正记录。顶层 JSON 数组表示多个独立批次，先前成功的批次保留，遇错停止且标准输出为空。
- `completions` → `TeamPlanner.completions(...)`。输入对象包含 `member_id`；返回该成员的完成记录数组，按 `completed_on`、`on`、`activity_id` 升序排列，无记录时为空数组。
- `schedule` → `TeamPlanner.member_schedule(...)`。输入对象包含 `member_id` 及可选 `from_on`、`to_on`、`status`。成员标识去除首尾空白，非字符串、空白或未知成员都会被拒绝。日期省略或为 `null` 时不限制对应边界，否则须为真实存在的 `YYYY-MM-DD`，范围包含两端并按活动日期筛选，起日晚于止日会被拒绝。`status` 默认为 `all`，只接受 `all`、`pending`、`completed`：后两者分别表示没有本人完成记录和已有本人完成记录，不随当前日期变化。结果只收录该成员已报名的活动，每项含 `activity_id`、`title`、`on`、`status`、`completed_on`、`conflict_activity_ids`；未完成时 `completed_on` 为 `null`。结果按 `on`、`activity_id` 升序排列，无匹配时为空数组。`conflict_activity_ids` 为该成员同日已报名的其他活动标识（去重、升序、排除自身），仅其他成员报名的活动不计入；同日已完成或被状态筛选隐藏的报名仍算冲突。查询不修改数据文件，空目录查询未知成员也不创建目录或文件。
- `enrollment-options` → `TeamPlanner.enrollment_options(...)`。在 `schedule` 只看已报名培训之外提供报名候选建议：输入对象包含 `member_id` 及可选 `from_on`、`to_on`、`available_only`。日期的含义、省略或为 `null` 不限边界、范围包含两端、起日晚于止日拒绝等校验与 `schedule` 完全一致；成员标识去除首尾空白，非字符串、空白或未知成员均抛出 `ValueError`；`available_only` 默认为 `false`，只接受布尔值。结果为数组，排除该成员已报名的所有活动（包括已完成但仍占席的活动），每项含活动原有的 `activity_id`、`title`、`on`、`capacity`，并增加 `remaining_seats`、`available`、`conflict_activity_ids`：剩余席位等于容量减当前报名人数（已完成报名也占席），`conflict_activity_ids` 只收录该成员同日已报名的其他活动标识（去重、升序；已完成报名照常计入，其他成员的报名不计入），`available` 仅在剩余席位大于零且冲突数组为空时为 `true`；满员与冲突同时存在时两项信息都保留。`available_only` 为 `true` 时只返回有空位且无同日冲突的候选，为 `false` 时返回全部候选。候选按 `on`、`activity_id` 升序排列，无匹配返回空数组。查询不依赖当前日期，取消、改报或改期后的查询反映最新席位与冲突；查询只读取数据，不改写 `data.json`，也不创建缺失的目录或文件，缺少完成记录字段的历史文件照常兼容。该命令只提供安排建议，不改变 `enroll` 原有的同日报名语义。
- `export-schedule` → `TeamPlanner.export_schedule(...)`。输入对象包含可选 `from_on`、`to_on`、`status`，含义与校验规则和 `schedule` 完全一致（日期省略或为 `null` 不限边界、范围含两端、起日晚于止日或非法 `status` 均抛出 `ValueError`，`status` 默认 `all`）。导出全员培训日程：每条现有报名占一行，未报名成员与无人报名的活动不产生行，已取消的报名不出现，已完成的报名仍保留。返回含 `csv` 字符串与 `row_count` 整数的对象，`row_count` 只统计数据行。表头固定为 `member_id,name,activity_id,title,on,status,completed_on,conflict_activity_ids`，数据行按 `on`、`activity_id`、`member_id` 升序排列，姓名与标题取当前档案，未完成的 `completed_on` 单元格为空。`conflict_activity_ids` 为紧凑 JSON 数组，列出本人同日其他已报名活动标识（去重、升序、排除本场；已完成或被状态筛选隐藏的报名仍计入，其他成员的报名不计入）。CSV 以逗号分隔，含逗号、双引号或换行的单元格加双引号且内部双引号写成两个，中文与原有换行无损保留，行结束符统一为 CRLF，不添加 BOM。没有匹配记录时仍返回表头且 `row_count` 为 0。导出只读取数据，不改写 `data.json`，也不创建缺失的目录或文件；缺少完成记录字段的历史文件按全部未完成处理。命令只把该对象以 JSON 打印到标准输出，不生成导出文件。
- `training-progress` → `TeamPlanner.training_progress(...)`。截至指定日期的多人培训核对：输入对象包含必填的 `activity_ids`、`as_of` 及可选 `member_ids`。`activity_ids` 必须是非空数组，活动标识去除首尾空白后须为非空字符串且规范化后不重复、每个活动均须存在；`as_of` 只接受无首尾空白、真实存在的 `YYYY-MM-DD` 字符串。`member_ids` 省略或为 `null` 表示全员，为空数组表示无人（结果 `members` 为空数组）；给出时必须是数组，成员标识去除首尾空白后须为非空字符串、规范化后不重复且均为已知成员。违反上述数组规则、传入非字符串或空白标识、规范化后重复或未知标识均抛出 `ValueError`。显式指定的成员按输入顺序返回，全员按成员标识升序返回。查询使用当前成员、名单和活动信息，只对完成日期应用截止日，不还原历史名单；其他成员的完成记录不影响本人，同名活动按标识分别核对，未来活动仍计入所选项目。结果对象含 `as_of`、`required_count`（即所选活动数，重复标识已被拒绝）与 `members`；成员项含 `member_id`、`name`、`completed_count`、`remaining_count` 与 `trainings`。各培训项按活动输入顺序给出 `activity_id`、`title`、`on`、`status`、`completed_on`：当前未报名时为 `not_enrolled`（`completed_on` 为 `null`）；已报名且本人完成日期不晚于截止日时为 `completed`；其余已报名（无记录，或完成日期晚于截止日）为 `pending`。完成日期保留当前记录的原值，无记录为 `null`；晚于截止日的记录在 `completed_on` 中仍可见但状态为 `pending`、不计为已完成。`remaining_count` 等于所选活动数减已完成数，未报名也算欠缺。小陈的完成日为 2026-10-18 时，截至 2026-10-16 计待完成，截至完成日当天计完成。查询不创建也不改写数据，不创建缺失的目录或文件；缺少 `completions` 的旧数据视为无记录，整份历史无效抛出 `ValueError`，读取文件的操作系统错误保留 `OSError`。
- `training-requirements` → `TeamPlanner.training_requirements(...)`。按培训组核对完成情况：同组完成任一场即满足一项要求，分组只用于本次查询，不保存，也不按标题推断。输入对象包含必填的 `groups`、`as_of` 及可选 `member_ids`。`groups` 必须是非空数组，每项是只含 `group_id` 与非空 `activity_ids` 数组的对象；所有标识去除首尾空白后须为非空字符串，规范化后组标识唯一，活动标识组内不重复且不跨组使用，每个活动均须存在。`as_of` 只接受无首尾空白、真实存在的 `YYYY-MM-DD` 字符串。`member_ids` 的选择与排序语义和 `training-progress` 完全一致（省略或 `null` 为全员并按成员标识升序、空数组为无人、给出时按输入顺序，拒绝重复与未知成员）。结果对象含 `as_of`、`required_count`（等于组数）与 `members`；成员项含 `member_id`、`name`、`completed_count`、`remaining_count` 与 `groups`。组项按输入顺序给出 `group_id`、`status`、`activity_id`、`completed_on`：本人在组内有不晚于截止日的完成记录时为 `completed`，一个组只计一次；多条合格记录按完成日期、活动日期、活动标识升序取首条，返回其活动标识与原完成日期。无合格记录但报名组内任一场时为 `pending`，完全未报名时为 `not_enrolled`，这两种状态的 `activity_id` 与 `completed_on` 均为 `null`。未来活动仍算要求，晚于截止日的记录不抵扣，其他成员记录不影响本人；`completed_count` 为完成组数，`remaining_count` 等于组数减完成组数，未报名也算欠缺。查询按当前档案、名单和完成记录核对，不还原历史名单，不依赖当前日期。上述输入不合法或整份历史无效均抛出 `ValueError`，不返回部分结果；成功和失败均不改写 `data.json`，也不创建缺失的目录或文件；缺少 `completions` 的旧数据按无记录处理，文件读取错误保留 `OSError`。
- `training-validity` → `TeamPlanner.training_validity(...)`。按培训组核对复训有效期：规则与 `training-requirements` 完全平行，原有核对方式保留不变。输入对象包含必填的 `groups`、`as_of` 及可选 `member_ids`。`groups` 必须是非空数组，每项是只含 `group_id`、非空 `activity_ids` 数组与 `valid_days` 的对象；所有标识去除首尾空白后须为非空字符串，规范化后组标识唯一，活动标识组内不重复且不跨组使用，每个活动均须存在；`valid_days` 必须是非布尔的正整数（`true` 不算 1）。字段缺失、多余字段或非法有效天数均抛出 `ValueError`，不返回部分结果。`as_of` 与 `member_ids` 的校验、选择顺序与 `training-requirements` 完全一致。每组只取本人完成日期不晚于截止日的最新记录：完成日期最晚者胜，完成日期相同时按活动日期、活动标识升序取首条，返回其活动标识与原完成日期；未来完成记录不参与选取，也不掩盖旧记录的过期状态。截止日距完成日的日历天数小于 `valid_days` 时为 `valid`，否则为 `expired`，两种状态都返回选中记录的 `activity_id` 与 `completed_on`；没有合格记录但当前已报名组内任一场时为 `pending`，完全未报名时为 `not_enrolled`，后两种状态的这两个字段为 `null`。未来活动仍计入要求。例如小陈于 2026-10-15 完成、有效三天时，截至 2026-10-17 为 `valid`，截至 2026-10-18 为 `expired`。结果结构与排序沿用 `training-requirements`，仅把成员的 `completed_count` 改为 `valid_count`（只统计 `valid` 组），`remaining_count` 等于总组数减有效组数，过期、待完成与未报名都计欠缺。查询按当前档案、名单和完成记录核对，不还原历史名单，也不依赖当天日期。输入不合法或整份历史无效均抛出 `ValueError`；成功和失败均不改写 `data.json`，也不创建缺失的目录或文件；缺少 `completions` 的旧数据按无记录处理，文件读取错误保留 `OSError`。
- `training-timeline` → `TeamPlanner.training_validity_timeline(...)`。按固定日期区间查看各成员每个培训组的状态变化：分组校验、标识规范化、有效天数与成员选择完全沿用 `training-validity`。输入对象包含必填的 `groups`、`from_on`、`to_on` 及可选 `member_ids`；`groups` 与 `member_ids` 的结构、标识校验和成员选择语义和 `training-validity` 完全一致（`valid_days` 必须是非布尔的正整数，`true` 不算 1；省略或 `null` 为全员并按成员标识升序、空数组为无人、给出时按输入顺序，拒绝重复与未知成员）。`from_on`、`to_on` 只接受无首尾空白、真实存在的 `YYYY-MM-DD` 字符串，起日不得晚于止日，相等表示只查询一天；非法输入、未知标识、逆序日期或整份历史无效均抛出 `ValueError`，不返回部分结果。结果对象含 `from_on`、`to_on`、`members`；成员项含 `member_id`、`name`、`groups`，成员与组都按既有选择顺序排列，成员选择为空数组时 `members` 为空数组但仍校验全部引用及整份历史。每个组项含 `group_id` 与 `periods`：各区间含 `from_on`、`to_on`、`status`、`activity_id`、`completed_on`，按起日升序排列，以闭区间完整覆盖查询范围且互不重叠。区间内每天的 `status`、`activity_id`、`completed_on` 与当日 `training-validity` 的对应组结果完全一致；连续日期这三项相同就合并为最长区间，任一项改变即分段，状态相同但完成依据（活动或完成日期）变化也要分段。记录选取规则与 `training-validity` 相同：只取不晚于当日的最新完成记录，完成日期最晚者胜，完成日期相同时按活动日期、活动标识升序取首条；未来完成记录不参与选取，也不遮盖旧记录。到期日（完成日加 `valid_days` 个日历天）当日转为 `expired`，此前为 `valid`；没有记录时当前已报名组内任一场为 `pending`，完全未报名为 `not_enrolled`，后两种状态的 `activity_id` 与 `completed_on` 为 `null`。例如小陈在 2026-10-15 完成且有效三天、没有其他完成记录时，查询同月 14 至 19 日得到一日 `pending`、三日 `valid`、两日 `expired`。有效期越过 9999-12-31 时只按查询范围给出状态，不报溢出错误。查询只使用当前档案、名单和已登记完成记录，不还原历史名单，也不依赖当天日期；成功和失败均不改写 `data.json`，也不创建缺失的目录或文件；缺少 `completions` 的旧数据按无记录处理，文件读取错误保留 `OSError`。命令沿用既有 JSON 输出、退出码（成功 0、错误 2 且标准输出为空、标准错误含 `error`）与顶层数组逐项执行语义，其他公开入口及 `demo` 行为不变。
- `training-alerts` → `TeamPlanner.training_alerts(...)`。集中查看已欠缺及即将到期的培训：规则与 `training-validity` 完全平行，原有核对方式保留不变。输入对象包含必填的 `groups`、`as_of`、`through_on` 及可选 `member_ids`；`groups`、`as_of`、`member_ids` 的结构、标识校验与成员选择语义和 `training-validity` 完全一致（`valid_days` 必须是非布尔的正整数，`true` 不算 1）。`through_on` 与 `as_of` 一样只接受无首尾空白、真实存在的 `YYYY-MM-DD` 字符串，且不得早于 `as_of`，否则抛出 `ValueError`，不返回部分结果。每个成员的每个组按既有有效期规则选取截至 `as_of` 的最新完成记录：完成日期最晚者胜，完成日期相同时按活动日期、活动标识升序取首条；未来完成记录不参与选取，也不掩盖旧记录。到期日为完成日加 `valid_days` 个日历天：到期日不晚于 `as_of` 时产生 `expired` 提醒，晚于 `as_of` 但不晚于 `through_on` 时产生 `expiring` 提醒，其余仍然有效的组不提醒。到期日晚于 9999-12-31 时视为窗口外不报溢出错误。没有合格记录时，当前已报名组内任一场产生 `pending` 提醒，否则产生 `not_enrolled` 提醒，两种欠缺都保留。结果对象含 `as_of`、`through_on`、`alerts`；每条提醒含 `member_id`、`name`、`group_id`、`status`、`activity_id`、`completed_on`、`expires_on`、`days_remaining`。有合格记录时后四项为所选活动标识、原完成日期、到期日及到期日减 `as_of` 的日历天数（允许零和负数）；`pending` 与 `not_enrolled` 的这四项为 `null`。提醒先按成员选择顺序（全员按成员标识升序）、再按组输入顺序排列；无提醒或成员选择为空数组时 `alerts` 为空数组。例如小陈于 2026-10-15 完成、有效三天时，2026-10-17 查至次日得到 `expiring`，2026-10-18 查询得到 `expired`。查询按当前档案、名单和完成记录核对，不还原历史名单，也不依赖当天日期。非法输入、未知标识或整份历史无效均抛出 `ValueError`，不返回部分结果；成功和失败均不改写 `data.json`，也不创建缺失的目录或文件；缺少 `completions` 的旧数据按无记录处理，文件读取错误保留 `OSError`。
- `renewal-options` → `TeamPlanner.training_renewal_options(...)`。在 `training-alerts` 的每条提醒上附带可报名的复训场次：输入对象包含必填的 `groups`、`as_of`、`through_on` 及可选 `member_ids`，参数、默认值、标识与日期校验语义和 `training-alerts` 完全一致（分组只用于本次查询，不保存，也不按标题推断）；即使没有提醒或 `member_ids` 为空数组，仍校验全部输入引用（未知活动或成员、跨组重复活动、非法日期等均抛出 `ValueError`）并校验整份历史，不返回部分结果。返回外层结构与 `training-alerts` 一致，仍为含 `as_of`、`through_on`、`alerts` 的对象；每条提醒保留原有全部字段、取值、状态判定与排列顺序（先成员选择顺序、再组输入顺序），只增加 `candidates` 数组，仍然有效的组不产生提醒，无提醒或成员选择为空数组时 `alerts` 为空数组。候选只来自该提醒所属组的活动：排除本人已经报名的全部场次（包括已完成但仍占席的场次），不跨组取场，也不按标题扩展分组；候选活动日期须落在 `as_of` 至 `through_on` 的闭区间，`expiring` 提醒还要求候选日期严格早于 `expires_on`（即最晚为到期日前一天），`expired`、`pending` 与 `not_enrolled` 提醒不加到期日限制。候选采用与 `enrollment-options` 完全相同的字段与既有计算口径：每项含 `activity_id`、`title`、`on`、`capacity`、`remaining_seats`、`available`、`conflict_activity_ids`，按 `on`、`activity_id` 升序排列；剩余席位等于容量减当前报名人数（已完成报名也占席，其他成员的报名只影响席位）；`conflict_activity_ids` 去重升序列出本人同日已报名的其他活动，包含本人在其他组的报名、已完成报名以及被本次窗口筛选隐藏的同日报名，但不包含任何其他成员的报名；满员与同日冲突同时存在时两类阻碍全部展示，仅当剩余席位严格大于零且冲突数组为空时 `available` 为 `true`。各候选独立评价：不为该成员预留席位，多个候选同时 `available` 也不代表多人或多场可以一并报名成功；没有候选时提醒照常保留且 `candidates` 为空数组。例如小陈于 2026-10-15 完成且有效三天，在 2026-10-18 查至 2026-10-20 时得到 `expired` 提醒；组内 10-19 的场次满员且与本人另一场同日冲突时仍列入候选但 `available` 为 `false`，组内 10-20 有剩余席位且无同日冲突的场次 `available` 为 `true`。查询使用当前档案、名单和完成记录，不还原历史名单，不依赖当天日期，也不假定参加即完成。非法输入、未知标识或整份历史无效均抛出 `ValueError`；成功和失败均不改写 `data.json`，也不创建缺失的目录或文件；缺少 `completions` 的旧数据按无记录处理，文件读取错误保留 `OSError`。命令沿用既有 JSON 输出、退出码（成功 0、错误 2 且仅标准错误含 `error`）与顶层数组逐项执行语义，其他公开入口及 `demo` 行为不变。
- `merge` → `TeamPlanner.merge_member(...)`。输入对象包含 `source_member_id`、`target_member_id`，分别为被合并成员与保留成员；标识去除首尾空白，非字符串、为空、两者相同或任一成员不存在都会被拒绝。被合并成员在各活动中的席位并入保留成员：仅其报名时在原位置替换为保留成员，两人都报名时保留一个位于两人中较早位置的席位，其余成员相对顺序不变，去重释放的名额可继续报名。完成记录仅一人有则归入保留成员；两人在同一活动都有记录时 `completed_on` 相同才合为一条，不同则拒绝整个合并（不选择日期、不覆盖记录）。成功返回保留成员对象并删除被合并成员档案。
- `merge-activities` → `TeamPlanner.merge_activities(...)`。同日多场培训合并：输入对象包含 `target_activity_id` 与 `source_activity_ids`，分别指定保留活动与非空来源数组。标识去除首尾空白，非字符串或空白标识、来源不是非空数组、规范化后来源重复、目标出现在来源中、任一活动未知或任一来源与目标日期不同均抛出 `ValueError`；活动标题可以不同，空名单来源也可合并。保留目标的标识、标题、日期、容量与额外字段：名单先保留目标原顺序，再按来源输入顺序及各自名单顺序追加未出现的成员，每人只占一席；最终去重人数超过目标容量时拒绝整次合并。只对原先未报名目标的转入成员检查最终同日冲突：全部来源移除后，本人仍报名其他同日活动时拒绝，已完成报名仍算冲突；目标原有成员的历史冲突、其他成员以及其他日期的冲突不阻止操作。完成记录并入目标：仅一处有记录则保留原日期，多处记录日期相同才合为一条，日期不同则拒绝整个合并（不选择或改写日期）；没有记录的成员仍为未完成，完成登记仍占席，操作不依赖当前日期。一次调用整体生效，返回完整目标活动对象，删除全部来源活动及其完成记录入口，来源额外字段随活动删除，不覆盖目标字段；名单、日程、完成记录查询与导出立即反映合并结果，旧来源标识随后按未知活动处理。成员档案、其他活动及其完成记录、顶层额外字段保持原样，缺少 `completions` 的旧数据按无记录处理。整份历史无效抛出 `ValueError`，文件读写错误保留 `OSError`；任一条件不满足均抛出 `ValueError`，业务拒绝时已有 `data.json` 字节不变，缺失目录或文件不创建。顶层 JSON 数组表示多个独立合并，先前成功的合并保留，遇错停止且标准输出为空。

登记完成不取消报名、不释放名额，也不改变名单顺序；同一成员在同一活动只能登记一次。`correct-completions` 只改动已有记录的日期或删除本人该条记录（撤销同样不取消报名、不释放名额），不新增记录、不影响其他成员；撤销后的报名回到未完成状态，取消、改报与改期重新按剩余完成记录执行原规则。活动或成员不存在、成员未报名、重复登记或完成日期早于活动日期都会被拒绝；`complete-batch` 将这些检查应用到整组，跨活动、跨成员的记录要么全部写入要么全部不写，规范化后重复的活动与成员组合同样整组拒绝。历史 `data.json` 没有完成记录字段时视为没有已完成培训。合并同样不额外拒绝同日多项报名；任何活动上的完成日期冲突都会拒绝整个合并，不留下部分结果，失败也不创建数据文件。改报在任一条件不满足时同样不修改两边名单及其他数据，失败前没有 `data.json` 也不会创建。

命令成功向标准输出打印 JSON 并返回 0；输入或本地文件错误向标准错误输出说明并返回 2。无参数的方法可省略输入文件。数据保存在 `root/data.json`，每次成功修改后保存；适用于单进程本地使用。

## 历史数据一致性

所有读取 `root/data.json` 的 API 与命令采用同一套校验标准。文件不存在时按空数据处理；文件存在时每次读取都校验**整份**数据，因此任何查询筛选都不会掩盖其他非法记录。数据有效时结果与以往一致；任一处无效时本次调用直接被拒绝（抛出 `ValueError`），不返回部分结果，已有文件字节不变，也不会因失败创建缺失的目录或文件。文件不是有效 UTF-8、不是有效 JSON、或顶层不是 JSON 对象同样抛出 `ValueError`；读取文件本身的操作系统错误（权限、`data.json` 是目录等）仍抛出 `OSError`。

- 顶层必须是 JSON 对象。缺少 `members`、`activities`、`completions` 任一字段时，该字段视为空集合；字段存在时必须是 JSON 对象，`null` 不算空对象。顶层允许有额外字段。
- 成员条目必须是对象：须有与外层键完全一致的 `member_id`，`name` 为非空白字符串，允许额外字段。
- 活动条目必须是对象：须有与外层键完全一致的 `activity_id`，`title` 为非空白字符串，`on` 为无首尾空白、真实存在的 `YYYY-MM-DD`，`capacity` 为非布尔的正整数（`true` 不算 1），`participants` 为数组，允许额外字段。
- 集合的外层键以及 `participants` 中的成员标识必须是无首尾空白的非空字符串。
- 参与者只能引用已存在的成员，不得有重复标识，人数不得超过容量；同一成员同日报名多项活动仍然合法。
- 完成记录的外层键必须引用已存在的活动；其值为对象，以该活动**已报名成员**标识为键、以真实 `YYYY-MM-DD` 完成日期为值，完成日期不得早于活动日期；空内层对象允许保留。
- 合法历史数据继续兼容：缺少 `completions` 字段表示没有完成记录，已完成报名继续占位；顶层、成员和活动对象上的额外字段在成功修改后原样保留，程序不会顺手修补旧文件。

命令遇到上述校验错误时标准输出为空，标准错误输出含 `error` 的 JSON 并返回 2；成功输出、`demo` 以及顶层输入数组逐项执行并保留此前成功操作的语义不变。

## 当前边界

当前只管理培训报名、取消报名与完成登记，不支持请假、排班、候补或权限系统。 不承诺并发写入或断电恢复。
